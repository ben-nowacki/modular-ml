# Git Branch & PR Guide

Reference material for branching, commit messages, pull requests, and rebasing in
the AmpWell repo. It extends the baseline agent rules (branch off `main` before
committing, `gh` CLI for GitHub, no interactive `-i` flags in the agent
environment) with the conventions this repo actually follows and the surrounding
best practice.

**Standing authorization for Mission Control task agents:** committing to your
task branch, pushing it to origin, and opening/updating the PR are
pre-authorized parts of your job. Never pause to ask permission for them.

Repo: `github.com/ampwell/ampwell-platform` · default branch: `main` ·
single remote `origin`.

**Observed baseline (from history):** commit subjects are terse, capitalized,
one line, no body, no conventional-commit prefix; history on `main` is **strictly
linear — zero merge commits** (`git log --merges` is empty), i.e. work lands via
squash or rebase, never a merge bubble. Keep that linearity.

---

## 1. Commit message format

### The rule

- **Subject line** is mandatory and does the heavy lifting — matching current
  history, most commits are subject-only. Capitalize the first word, no full
  stop, keep it under ~72 chars. Describe the change, not the file
  (`Better command retry logic and timeouts`, not `Edit command_loop.py`).
- **No conventional-commit prefixes.** This repo does not use `feat:` / `fix:` /
  `chore:`. Don't introduce them — stay consistent with the existing log.
- **Body is optional but expected for non-trivial changes.** A one-line tweak
  needs no body; a security fix, a data migration, or anything with a non-obvious
  rationale should carry a `Why:` paragraph. Explain *why*; the diff already
  shows *how*.
- **One logical change per commit.** If the subject needs an "and" joining two
  unrelated things, it's probably two commits. (Historic exception:
  wide-but-cohesive sweeps like `Security improvements and tag handling on file
  artifacts` are fine when the changes are genuinely one theme.)

Treat any repository PR template as structural guidance, not text to copy. Use
its meaningful concepts, headings, and approximate section order while replacing
instructions and placeholders with concise facts about the actual change. The
completed PR must not contain an untouched template followed by separate notes.

Never identify Claude, Codex, an AI, or an agent as an author, co-author,
contributor, generator, or source of the work. This prohibition covers commit
subjects, bodies, and trailers; PR titles, bodies, and comments; documentation;
and every other part of commit or pull-request history. In particular, never add
`Co-authored-by`, `Generated by/with`, signatures, badges, or similar
attribution. This does not restrict the pre-authorized push and PR operations.

### Examples

Good — subject only (the common case):

```
Add device_limits table and firmware-versioned overrides
```

Good — subject + body for something non-obvious:

```
Purge legacy agent hmac_secret_hash for KEK-migrated agents

The legacy column stored sha256(raw_secret), which is itself a usable
signing key, so a table dump without the KEK could forge agent commands.
NULL it out wherever an encrypted secret already exists; leave un-migrated
agents untouched since it's their only credential.
```

Avoid:

```
fix stuff              # vague, lowercase, no context
Updated files.         # says nothing; trailing period
feat(api): add route   # conventional-commit prefix this repo doesn't use
WIP                    # never land WIP on a shared branch
```

## 2. Branch naming

Never commit directly to `main` — branch first. Use a `type/short-slug` form,
lowercase, hyphen-separated, no spaces:

| Type | Prefix | Use for | Example |
|------|--------|---------|---------|
| Feature | `feature/` | New functionality, endpoints, migrations, UI | `feature/protocol-run-history` |
| Hotfix | `hotfix/` | Urgent prod fix that jumps the normal queue | `hotfix/hmac-nonce-replay` |
| Fix / bug | `fix/` | Non-urgent bug fix | `fix/protocol-lock-cascade` |
| Experiment | `experiment/` (or `spike/`) | Throwaway exploration, may never merge | `experiment/sse-live-channels` |
| Chore / infra | `chore/` | Tooling, deps, CI, config | `chore/bump-orval` |

Naming guidance:

- **Slug = what, not who.** `feature/device-limits`, not `feature/ben-work`.
- **Keep it short** (2–4 words). The PR title carries the full description.
- **Feature vs. hotfix is about urgency and base, not size.** A feature branches
  off current `main` and rides the normal review/deploy cadence. A **hotfix**
  targets a production incident: branch off the deployed state, keep the diff as
  small as possible, fast-track review, and deploy immediately after merge (see
  `developer_guide.md` → *Deploy with a migration* / service restart).
- **Experiments are explicitly disposable.** Prefix `experiment/`, don't hold
  them to the same commit hygiene, and delete them when the question is answered.
  If an experiment turns real, open a fresh `feature/` branch and cherry-pick or
  re-implement the good parts with clean commits — don't promote the messy
  experiment history.
- **Delete branches after merge.** Squash-merge leaves the branch redundant.

## 3. Pull request description — required contents

Open PRs with `gh pr create`. A PR description is the durable record of *why* a
change exists; keep it self-contained and written for reviewers.

Treat the repository's PR template as an outline, not as content to paste. Read
it, identify its meaningful concepts and order, then write a tailored
description using the repository's headings where they help. Never paste the
untouched template and add notes above or below it. Remove instructional text,
HTML comments, placeholders, irrelevant checklists, and unused headings.

Cover these concepts, following the repository template's approximate order:

1. **Description / summary and motivation** — what changed and why.
2. **Related issues, tasks, or specs** — use `Closes #123` when appropriate,
   or link/name the task or spec that prompted the work.
3. **Changes / implementation details** — notable behavior and reviewer
   hotspots, grouped by area when useful.
4. **Testing / checks** — exact commands or manual steps and their outcomes;
   state failures or unrun checks honestly.
5. **Migrations, data, security, or risk impact** — include when relevant and
   explicitly say `None` or `Not applicable` when silence could be ambiguous.
6. **Notes / follow-ups** — known gaps, deferred work, and intentional scope
   boundaries, only when useful.

Rules:

- **Summary, related work, changes, and testing are the standard minimum.**
  Adapt labels to the repository template and consolidate overlapping sections;
  do not create empty sections merely to reproduce every heading.
- **Preserve semantic ordering, not boilerplate.** The finished PR should read
  like a completed review document, never a blank form followed by agent notes.
- **Title matches the merge commit you want.** With squash-merge the PR title
  becomes the commit subject on `main`, so write it to the §1 subject standard.
- **Never paste secrets, tokens, `.env` contents, or the KEK** into a PR body —
  it's published to GitHub.

## 4. Squash vs. preserve commits

Default is **squash-merge** — it's what keeps `main` linear and one-commit-per-
change, matching the existing history.

**Squash (default) when:**

- The branch is one logical change, however many WIP commits it took.
- Intermediate commits are noise (`fix typo`, `address review`, `oops`).
- You want the PR title/description to become the single `main` commit.

**Preserve individual commits (rebase-merge, no squash) when:**

- The branch is a genuine *sequence* of independently meaningful, individually
  reviewable, individually revertible steps — e.g. `migration` → `model` →
  `endpoint` → `frontend`, each self-contained and green.
- Each commit already meets the §1 standard (clean subject, passes tests) and the
  history tells a story worth keeping.

**Never** use a merge commit (`--no-ff`) — that breaks the linear history this
repo maintains. If you preserve commits, do it via rebase so they land in a
straight line.

Before merging either way, **clean the branch locally first**: rebase onto latest
`main`, and if preserving commits, reorder/reword/drop as needed so what lands is
what you'd want to read in a year. (Interactive rebase `git rebase -i` is for
human devs at the terminal; the agent environment doesn't support `-i`, so agents
should squash at merge time via the PR instead.)

## 5. Resolving a rebase conflict — step by step

Rebasing keeps history linear by replaying your branch's commits on top of the
latest `main`. Prefer it over merging `main` into your branch.

**1. Update `main` and start the rebase.**

```bash
git fetch origin
git rebase origin/main          # from your feature branch
```

**2. If it stops on a conflict, see what's affected.**

```bash
git status                      # lists "both modified" files
```

Git pauses at the first conflicting commit. The working tree has that commit
partially applied, with conflict markers in the clashing files.

**3. Open each conflicted file and resolve the markers.**

```
<<<<<<< HEAD
    code already on main (the "ours" side during a rebase)
=======
    code from your commit being replayed (the "theirs" side)
>>>>>>> <commit subject>
```

Note the rebase inversion: during a rebase **`HEAD`/"ours" is `main`**, and
"theirs" is *your* commit — the opposite of a merge. Edit the file to the correct
combined result and **delete all three marker lines**. Resolve by intent, not by
blindly taking one side.

**4. Stage the resolved files and continue.**

```bash
git add <resolved-file> ...
git rebase --continue           # opens the commit message; keep or adjust it
```

Repeat 2–4 for each commit the rebase stops on. Don't run `git commit` yourself
during a rebase — `--continue` handles it.

**5. Verify, then force-push (with lease).**

```bash
# run the relevant checks — a clean rebase can still be logically broken
cd backend && uv run pytest        # and/or: cd frontend && npm run build
git push --force-with-lease        # history was rewritten, so a normal push is rejected
```

Always `--force-with-lease`, never a bare `--force`: the lease refuses to
clobber the remote if someone else pushed to your branch since you last fetched.

**Bail-out and helpers:**

- `git rebase --abort` — give up and return to the pre-rebase state, no harm done.
  Use it whenever the conflict is bigger than expected and you want to regroup.
- `git rebase --skip` — drop the current commit entirely (only if it's genuinely
  redundant — e.g. its change already exists on `main`).
- `git checkout --ours <file>` / `--theirs <file>` — take one whole side when you
  are certain (remember the rebase inversion: `--ours` = `main`).
- `git config rerere.enabled true` (once, locally) — records how you resolved a
  conflict so an identical one later resolves itself. Handy on long-lived
  branches rebased repeatedly.

**Golden rule:** only rebase/force-push branches that are yours. Never rebase a
shared branch or `main` itself — rewriting shared history breaks everyone who has
it checked out.

## 6. Quick checklist

- [ ] Branched off `main` with a `type/short-slug` name; didn't commit to `main`.
- [ ] Commit subjects: capitalized, ≤ 72 chars, no period, no `feat:`-style prefix.
- [ ] Body added for anything non-obvious (with a `Why:`), else subject-only.
- [ ] NO CLAUDE, CODEX, AI, OR AGENT ATTRIBUTION IN COMMITS OR PR HISTORY.
- [ ] Rebased onto latest `origin/main`; history stays linear (no merge commits).
- [ ] PR body covers summary, related work, changes, testing, and applicable
      impacts in the repository template's semantic order.
- [ ] Squash unless the commits are individually meaningful; force-push only with
      `--force-with-lease`.
- [ ] Pushed the task branch and opened the PR without waiting to be asked —
      that is part of the task, not something needing consent.
